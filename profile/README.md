<h2>一、先分清四层，别在同一层反复换服务商</h2>
<p>「用什么国家 IP」这个问题，答案取决于你卡在哪一层。有人真实问题是出口归属地和账号注册地不一致，有人出口选对了但长连接总在半夜被掐，还有人前两样都稳，只是没人盯着，断了两个小时才从业务日志里发现。三种情况要动的地方完全不同，混着讨论就会变成「换一家试试」，换完还是老样子。</p>
<p>分层的好处是每层有自己的输入、输出和验收口径，上层不稳时不要动下层。出口归属还没确认就去调重试逻辑，等于在漏水的桶上换水龙头。下面这张表是四层的分工，建议直接抄进团队的排查手册。</p>

<h2>二、出口层：国家定下来，要固定的是归属信息</h2>
<p>国家只是第一层筛选。同一个国家里，机房段和住宅段的差别比国与国之间还大。选定国家之后，真正要固定的是三样东西：ASN 归属、时区、地理坐标。这三样对齐了，账号在平台上看起来才像一直住在同一个地方。</p>
<img src="/tp.png" alt="Claude API 长期任务按国家分层固定住宅出口的排查示意">
<p>核验方式不复杂，公开入口就够用。<code>ipinfo.io</code> 查 ASN 和城市，<code>ip.sb</code> 看 IP 类型标注，再看时区字段是否和账号注册时填的地区一致。三个来源结论一致才往下走。如果 ASN 显示的是托管商、云厂商或者带 hosting 字样，那不管销售页怎么写，它都不是住宅出口。</p>
<h3>国家怎么定：跟着账号注册地走，不跟着办公地走</h3>
<p>常见误区是「我们团队在深圳，那就选香港」。平台看的是账号当初注册时留下的地区痕迹，不是你现在坐在哪。注册地在美国的号长期挂香港出口，等于每天在跨区登录，风控评分会慢慢往上堆。正确做法是按账号的注册地分批，每批锁定一个国家，同一批只在同一个国家内做线路轮换。</p>
<h3>同批同地区：把变量收敛到一个</h3>
<p>手上几十个号一起跑，最省事的做法是整批锁一个国家甚至一个城市。代价是出口资源的选择面变窄，好处是出问题时排查范围极小——所有号的环境特征一致，谁的表现掉到平均线以下，一眼就能挑出来。混着放反而复杂：出问题时分不清是号的问题还是地区的问题。</p>
<h3>什么情况下才允许跨地区</h3>
<p>只有一种情况值得跨区：业务本身要验证新市场。这时候正确的做法不是把老号搬过去，而是另起一批新号落在新地区，老号继续待在原地。老号的注册地和登录地一旦分叉，恢复成本比新开一批号高得多。</p>

<h2>三、会话层：半夜断连，多数是连接被中间设备重置</h2>
<p>出口干净但任务照样断，问题通常在会话层。表现是跑着跑着一批请求全部超时，日志里成片出现 connection reset 或者 502。这类现象九成不是模型侧的问题，而是中间链路上的设备把长连接当空闲连接清掉了。</p>
<h3>保活参数怎么设</h3>
<p>把 TCP keepalive 打开，空闲探测间隔设到 60 秒以内，比多数 NAT 设备的会话老化时间短。HTTP 客户端层再叠一层应用级心跳，间隔 30 到 45 秒，请求体做到极小。两层都开之后，单连接存活时长通常能从几十分钟拉到数小时。判定阈值可以参考：连续 24 小时内连接重置次数低于 3 次算正常，超过 10 次说明链路上有设备在主动干预。</p>
<h3>重试要退避，而且请求必须幂等</h3>
<p>掉线后立刻重试是最常见的错误，会在恢复瞬间把并发打满，反而让上游判定为异常流量。用指数退避，起始 2 秒，上限 60 秒，加随机抖动。同时确认业务请求是幂等的，否则重试会造成重复计费和重复写入。这两件事在代码里各写十行，收益比换线路大得多。</p>

<h2>四、冗余层：备用线路要提前跑热，不是断了才配</h2>
<p>双 ISP 的价值不在于「有两条」，而在于切换的那一刻备用线路已经处于可用状态。很多团队配了备用，真断了才发现备用线路的出口落在另一个城市，或者备用通道根本没做过连通性验证，切过去直接被判异常，比不切更糟。</p>
<h3>分流口径：按账号分，不按请求分</h3>
<p>同一个账号的请求不要在主备之间来回跳。今天走 A 线明天走 B 线，出口一变，账号的地理轨迹就断了。正确口径是一个账号固定一条主线路，备用只在主线路不可用时接管，且备用出口要落在同一个城市、同一个运营商体系内。切换后保持至少 30 分钟不再回切，避免来回抖动。</p>
<h3>预热怎么做</h3>
<p>备用线路每周做一次主动检查：拉一次接口、跑一次鉴权、确认出口 IP 与预期一致。检查结果记进表里，和主线路放在一起对比。这件事交给定时任务，不要靠人记得。</p>

<h2>五、运维层：把掉线变成能查到的事件</h2>
<p>前四层做得再好也会有意外。运维层的作用是让意外在几分钟内被发现，而不是在客户投诉之后。这一层不需要复杂工具，三个字段就够：每个请求记录出口 IP、响应状态、耗时；每条线路记录当日重置次数；每次切换记录触发原因和耗时。</p>
<h3>监控看三个数就够</h3>
<p>第一个是错误率，按线路维度统计，单线路 5 分钟内错误率超过 5% 触发告警。第二个是首字节时间，超过基线两倍就要看。第三个是出口 IP 变化，同一账号的出口在没有人工操作的情况下变了，立刻查。</p>
<h3>交接记录要能复现环境</h3>
<p>团队换人时最耗时的不是讲业务，是讲这个号配的是哪条线、哪个浏览器配置。把账号、出口、配置三项写进一张表，谁接手照着表就能复原。这条看着和掉线无关，实际上决定了出问题时能不能快速定位。</p>

<h2>常见问答</h2>
<h3>同一批号必须用同一个国家的 IP 吗？</h3>
<p>答：不强制，但建议这么做。同一批号锁同一个国家甚至同一个城市，能把排查变量收敛到一个，出问题时对比同行号的表现就能定位。跨国混放只在验证新市场时才值得，而且应该新起一批号，不要把老号搬过去。</p>
<h3>用了住宅 IP 就不会掉线了吗？</h3>
<p>答：不会。住宅属性解决的是「看起来像真实用户」，解决不了链路质量。掉线多半来自中间设备清理长连接、线路拥塞或者客户端重试策略不当。选对出口只是第一步，保活和重试还得自己配。</p>
<h3>双 ISP 出口是不是两条可以同时跑？</h3>
<p>答：不建议同一个账号同时用。同一账号在两条出口上并发，出口 IP 不一致，反而容易触发校验。合理用法是主用一条、另一条待命，切换后保持一段时间不回切。</p>
<h3>怎么判断一条线路值不值得长期挂？</h3>
<p>答：看三个数：连续 72 小时的重置次数、首字节时间的波动幅度、出口 IP 是否稳定不变。三项都稳的线路才值得按包月走。只测十分钟就下单，后面大概率要重新挑。</p>
